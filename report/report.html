주요 발견

  • PKCE가 기본적으로 강제됨 — client_secret_basic을 쓰는 confidential 클라이언트에서도 code_challenge 없이 /oauth2/authorize 요청 시 invalid_request: OAuth 2.0 Parameter: code_challenge 오류 발생. 별도 설정(require-proof-key) 없이도 최신 Spring Security가 기본으로 PKCE를 요구하는 것으로 확인됨. OAuth 2.1 권고사항 반영으로 추정.
  • MySQL / MyBatis / Redis는 Step 0에서 의도적으로 배제(계획대로 필요한 Step에서 점진 도입).

테스트 방법 (재현 가능한 curl 시퀀스)

로컬에서 세 모듈이 기동 중이어야 합니다: ./gradlew :auth-server:bootRun, :gateway:bootRun, :resource-server:bootRun (포트: auth-server 9000 / gateway 18080 / resource-server 18081 — 다른 프로젝트와의 포트 충돌을 피하기 위해 8080/8081 대신 18080/18081 사용).

OIDC 디스커버리 확인: http://localhost:9000/.well-known/openid-configuration

로그인 계정: user / password

# 1) PKCE code_verifier / code_challenge(S256) 생성
VERIFIER=$(openssl rand -base64 96 | tr -d '=+/\n' | cut -c1-64)
CHALLENGE=$(printf '%s' "$VERIFIER" | openssl dgst -sha256 -binary | openssl base64 | tr -d '=' | tr '+/' '-_')

# 2) 로그인 (쿠키 저장)
curl -c cookies.txt -b cookies.txt http://localhost:9000/login -o login.html
CSRF=$(grep -o 'name="_csrf" type="hidden" value="[^"]*"' login.html | sed -E 's/.*value="([^"]*)"/\1/')
curl -c cookies.txt -b cookies.txt -X POST http://localhost:9000/login \
  --data-urlencode "username=user" --data-urlencode "password=password" \
  --data-urlencode "_csrf=$CSRF"

# 3) 인가 요청 (PKCE 포함) → 동의 화면 HTML 수신
curl -c cookies.txt -b cookies.txt -G http://localhost:9000/oauth2/authorize \
  --data-urlencode "response_type=code" --data-urlencode "client_id=demo-client" \
  --data-urlencode "scope=openid profile" \
  --data-urlencode "redirect_uri=http://127.0.0.1:18080/authorized" \
  --data-urlencode "state=xyz123" \
  --data-urlencode "code_challenge=$CHALLENGE" --data-urlencode "code_challenge_method=S256" \
  -o authorize.html

# 4) 동의 제출 → redirect_uri로 302, code 파라미터 획득
STATE=$(grep -o 'name="state" value="[^"]*"' authorize.html | sed -E 's/.*value="([^"]*)"/\1/')
curl -c cookies.txt -b cookies.txt -i -X POST http://localhost:9000/oauth2/authorize \
  --data-urlencode "client_id=demo-client" --data-urlencode "state=$STATE" \
  --data-urlencode "scope=profile"
# → Location 헤더의 code= 값을 복사

# 5) 토큰 교환
curl -u demo-client:secret -X POST http://localhost:9000/oauth2/token \
  --data-urlencode "grant_type=authorization_code" --data-urlencode "code=<위에서 복사한 code>" \
  --data-urlencode "redirect_uri=http://127.0.0.1:18080/authorized" \
  --data-urlencode "code_verifier=$VERIFIER"

# 6) 게이트웨이 경유 리소스 접근
curl http://localhost:18080/api/hello -H "Authorization: Bearer <access_token>"
# => {"message":"hello, user"}

Step 1 — 항목 3: 인증/인가 방식 (토큰 / 세션 / 쿠키)

✔ 확인 완료 — resource-server에 두 개의 SecurityFilterChain을 @Order로 나란히 두고 대조: /api/**는 OAuth2 Resource Server(JWT 검증), /web/**는 폼 로그인 + 세션 쿠키.

결론 요약

토큰(JWT) — /api/**세션-쿠키 — /web/**
인증 상태 저장 위치서버에 없음 — 토큰 자체에 서명된 클레임 포함(stateless)서버 메모리(HttpSession)에 SecurityContext 저장(stateful)
클라이언트 전달 방식Authorization: Bearer <jwt> 헤더 — API/모바일/SPA에 적합JSESSIONID 쿠키 — 브라우저 전통적 폼 로그인에 적합
인증 실패 시 동작401 + WWW-Authenticate: Bearer 헤더 (리다이렉트 없음)302 리다이렉트 → /login (브라우저 친화적)
검증 방법auth-server의 JWK로 서명 검증(issuer-uri 기반), auth-server에 매 요청마다 조회하지 않음매 요청마다 세션 스토어 조회 필요
만료/폐기토큰 자체 exp 클레임으로 자연 만료(서버가 능동적으로 끊기 어려움 — Step 6에서 다룸)세션을 서버에서 즉시 무효화 가능(Step 6에서 다룸)

참고: /api/** 체인도 기본 설정에서는 요청 시 JSESSIONID 쿠키를 함께 내려준다(Spring Security 기본 세션 정책 때문). 완전한 stateless를 원하면 sessionManagement(session -> session.sessionCreationPolicy(SessionCreationPolicy.STATELESS))를 명시적으로 추가해야 한다 — 이번 데모에서는 기본값을 그대로 두고 이 차이만 기록.

하이브리드 패턴(구현하지 않고 개념만 기록): 실무에서는 게이트웨이/BFF가 브라우저에는 세션 쿠키만 내려주고, 내부적으로는 그 세션에 연결된 access token을 꺼내 백엔드 API에 Bearer로 전달하는 방식(OAuth2 Client + 세션)도 흔히 쓰인다. 이번 조사 범위(6개 항목)에는 해당 항목이 없어 별도 구현은 하지 않음.

테스트 방법

# (a) 토큰 방식 — Bearer 있음/없음 비교
curl -i http://localhost:18081/api/hello -H "Authorization: Bearer <access_token>"   # 200
curl -i http://localhost:18081/api/hello                                              # 401 + WWW-Authenticate

# (b) 세션 방식 — 로그인 없이 접근
curl -i http://localhost:18081/web/hello        # 302 → /login

# (b) 세션 방식 — 로그인 후 쿠키로 접근
curl -c cookies.txt -b cookies.txt http://localhost:18081/login -o login.html
CSRF=$(grep -o 'name="_csrf" type="hidden" value="[^"]*"' login.html | sed -E 's/.*value="([^"]*)"/\1/')
curl -c cookies.txt -b cookies.txt -X POST http://localhost:18081/login \
  --data-urlencode "username=user" --data-urlencode "password=password" --data-urlencode "_csrf=$CSRF"
curl -b cookies.txt http://localhost:18081/web/hello
# => {"message":"hello (session), user"}

직접 열어볼 수 있는 링크: http://localhost:18081/login (user/password로 로그인 후 /web/hello 접근 가능)

Step 2 — 항목 2: 인증 절차 커스텀 (2FA)

✔ 확인 완료 — 가능하며, Spring Security 7.1(Boot 4.1 번들)이 공식 다단계 인증(MFA) 프레임워크를 내장하고 있어 직접 필터를 짜지 않고도 구현 가능하다. 비밀번호(1차) → OTP(2차, 문자/메일 대신 콘솔 로그로 mock) 순서로 로그인해야 보호된 리소스(OAuth2 인가 엔드포인트 포함)에 접근할 수 있도록 구성했다.

결론 요약

  • @EnableMultiFactorAuthentication + http.oneTimeTokenLogin(...) 조합만으로 "1차 인증 → 2차 인증(OTP)" 흐름이 구현된다. 로그인할 때마다 서버가 FactorGrantedAuthority(예: FACTOR_PASSWORD, FACTOR_OTT)를 세션의 Authentication에 누적시키고, 지정한 팩터가 모두 모여야 리소스 접근이 허용된다.
  • OTP 전송 채널(문자/메일 등)은 OneTimeTokenGenerationSuccessHandler를 직접 구현해 완전히 커스텀 가능 — 이번 데모는 실제 발송 대신 콘솔 로그로 mock(범위 외).
  • 필요한 팩터가 부족하면 서버가 자동으로 "부족한 팩터" 로그인 화면으로 리다이렉트한다(/login?factor.type=ott&factor.reason=missing) — 별도의 라우팅 코드를 작성할 필요가 없다.

주의할 점 (실제로 겪은 함정)

  • @EnableMultiFactorAuthentication(authorities=...)를 그대로 쓰면 전역으로 적용된다. 즉 리소스 오너가 로그인하는 /oauth2/authorize뿐 아니라, OAuth2 클라이언트가 client_secret_basic(Basic Auth)로 호출하는 /oauth2/token까지 "두 팩터 모두 보유"를 요구하게 되어 정상적인 토큰 교환 요청이 403으로 거부되는 문제를 실제로 겪었다. 클라이언트 인증은 애초에 FactorGrantedAuthority 체계 대상이 아니기 때문이다.
    해결: authorities = {}로 애너테이션을 두어(필터 간 팩터 누적 메커니즘만 활성화) 전역 강제는 끄고, AuthorizationManagerFactories.multiFactor().requireFactors(...).build().authenticated()로 만든 AuthorizationManager를 /oauth2/authorize 경로에만 .access(...)로 선택 적용했다.
  • MyBatis Spring Boot Starter 3.0.4가 Boot 4.1에서 자동으로 동작하지 않음 — MybatisAutoConfiguration의 @ConditionalOnSingleCandidate(DataSource.class)가 "빈을 찾지 못함"으로 평가되어 SqlSessionFactory가 자동 생성되지 않았다(Boot 4.1의 재구성된 자동구성 패키지 구조와 버전이 맞지 않는 것으로 추정 — Step 0에서 우려했던 지점이 실제로 발생). SqlSessionFactory 빈을 직접 정의해 우회했다(MyBatisConfig.java).

테스트 방법 (재현 가능한 curl 시퀀스)

로그인 계정은 이제 MySQL(MyBatis) 조회로 검증된다: user / password. auth-server 콘솔 로그에서 [MOCK SMS/EMAIL] OTP code for user: ... 줄을 확인해 OTP 값을 얻는다.

# 1) 1차 인증 (비밀번호)
curl -c c.txt -b c.txt http://localhost:9000/login -o login.html
CSRF=$(grep -o 'name="_csrf" type="hidden" value="[^"]*"' login.html | sed -E 's/.*value="([^"]*)"/\1/')
curl -c c.txt -b c.txt -X POST http://localhost:9000/login \
  --data-urlencode "username=user" --data-urlencode "password=password" --data-urlencode "_csrf=$CSRF"

# 2) OTP 요청 (문자/메일 대신 콘솔 로그로 mock 발송)
curl -c c.txt -b c.txt http://localhost:9000/login -o login2.html
CSRF2=$(grep -o 'name="_csrf" type="hidden" value="[^"]*"' login2.html | sed -E 's/.*value="([^"]*)"/\1/')
curl -c c.txt -b c.txt -X POST http://localhost:9000/ott/generate \
  --data-urlencode "username=user" --data-urlencode "_csrf=$CSRF2"
# => auth-server 콘솔 로그에서 OTP 값 확인

# 3) 2차 인증 (OTP 제출)
curl -c c.txt -b c.txt http://localhost:9000/login/ott -o ott.html
CSRF3=$(grep -o 'name="_csrf" type="hidden" value="[^"]*"' ott.html | sed -E 's/.*value="([^"]*)"/\1/')
curl -c c.txt -b c.txt -X POST http://localhost:9000/login/ott \
  --data-urlencode "token=<위에서 확인한 OTP>" --data-urlencode "_csrf=$CSRF3"

# 4) 이제 /oauth2/authorize 접근 가능 (두 팩터 모두 보유) — 이후 Step 0과 동일하게 토큰 교환

직접 확인 가능한 링크: http://localhost:9000/login (로그인 페이지에 비밀번호 폼과 "Request a One-Time Token" 폼이 함께 표시됨을 확인 가능)

Step 3 — 항목 1: 로그인 UI 커스텀 / 외부 배치

✔ 확인 완료 — 가능하다. auth-server(:9000)와 완전히 별도로 배포된 React 앱(:5180)에 로그인 폼을 두고, 인증되지 않은 사용자가 /oauth2/authorize에 접근하면 auth-server가 그 외부 URL로 리다이렉트하도록 구성했다. 로그인 성공 후에는 원래 요청(/oauth2/authorize?...)으로 자동 복귀한다.

결론 요약 — 표준 패턴인가?

  • 표준 패턴(문서화된 공식 확장 지점)이다. formLogin().loginPage(url)은 Spring Security가 처음부터 지원하는 커스터마이징 포인트이며, url에 자신의 도메인이 아닌 절대 URL(외부 앱 주소)을 넣는 것도 정상 동작한다. 별도 컨트롤러나 리버스프록시가 필요 없다.
  • 인증 자체는 여전히 OAuth2 Authorization Code(+PKCE) 흐름 그대로다 — 로그인 화면의 위치만 바뀌었을 뿐, auth-server가 세션 쿠키를 발급/검증하고 /oauth2/authorize → 동의 → /oauth2/token으로 이어지는 프로토콜은 동일하다.
  • 이번 데모는 React가 네이티브 HTML <form method="POST">로 자격증명을 auth-server의 /login에 직접 제출하는 방식을 택했다. 이는 전체 페이지 이동(top-level navigation)이라 브라우저의 동일-출처 정책(CORS) 제약을 받지 않는다 — 즉 CORS 설정이 전혀 필요 없다. 대신 React 앱과 auth-server가 서로 다른 origin(:5180 vs :9000)이므로 fetch로 로그인을 처리하려 했다면 CORS + 쿠키(credentials: 'include') + CSRF 토큰 교환까지 추가로 구성해야 했을 것이다(비표준/더 복잡한 경로).

주의할 점

  • CSRF: 기본적으로 Spring Security는 상태 변경 요청(POST)에 CSRF 토큰을 요구한다. 외부 React 페이지는 auth-server의 세션에 바인딩된 CSRF 토큰 값을 알 방법이 없으므로(별도 origin), 이번 데모는 POST /login에 한해 CSRF 검증을 예외 처리했다(csrf.ignoringRequestMatchers("/login")). 프로덕션에서는 CookieCsrfTokenRepository.withHttpOnlyFalse()로 JS가 읽을 수 있는 CSRF 쿠키를 내려주고 React가 그 값을 읽어 제출하는 방식이 더 안전하지만, 이번 조사 범위(가능 여부 확인)에서는 생략했다.
  • 이번 프로젝트는 2FA(Step 2)가 함께 켜져 있는데, 1차(비밀번호) 로그인 화면만 외부로 옮겼다. 2차(OTP 제출) 화면은 여전히 auth-server가 직접 렌더링하는 기본 페이지(/login/ott)를 사용한다 — "로그인 UI를 외부에 둘 수 있는가"라는 질문 자체는 1차 화면만으로 충분히 답이 되므로 범위를 넘겨 2차 화면까지 옮기지 않았다.
  • formLogin().loginPage(externalUrl)을 쓰면 auth-server 자신의 GET /login 페이지에서 비밀번호 폼이 사라진다(그 URL은 "당신이 직접 제공하는 페이지"라는 뜻이 되기 때문). 실제로 확인해보니, OTT 로그인 설정이 공유하는 /login 경로에는 이제 "OTP 요청" 폼만 남고 비밀번호 폼은 표시되지 않는다.

Step 4 — 항목 4: 로그아웃 / 토큰 만료

✔ 확인 완료 — 세션 방식과 토큰 방식은 로그아웃/만료 처리 방식이 근본적으로 다르다는 것을 실제로 확인했다. 특히 토큰 revocation이 이미 발급된 JWT 자체를 무효화하지는 않는다는 점이 가장 중요한 발견이다.

결론 요약

세션-쿠키 방식토큰(JWT) 방식
로그아웃POST /logout → 서버가 세션을 즉시 파기. 이후 같은 쿠키로 요청하면 로그인 페이지로 리다이렉트됨(실측 확인).POST /oauth2/revoke는 AS 내부 저장소에서 해당 토큰의 인가 기록을 지울 뿐, 이미 발급된 JWT 자체는 서명이 유효한 한 계속 통과된다(아래 실측 참고).
만료세션 타임아웃(서버 설정) 시 자동 만료.exp 클레임으로 자체 만료. 단, Spring Security 기본 JwtTimestampValidator는 60초 clock-skew 유예를 두므로 exp 이후에도 최대 60초간 더 유효할 수 있다(아래 실측 참고).
클라이언트가 해야 할 일없음(쿠키 삭제는 브라우저가 처리, 서버가 실질적 무효화를 담당).로그아웃 시 access/refresh 토큰을 클라이언트가 직접 폐기(저장소에서 삭제)해야 함. 서버의 revoke 호출만으로는 이미 배포된 JWT를 회수할 수 없기 때문.

실측: revocation이 JWT를 무효화하지 못함

# access_token revoke -> 200 OK (성공)
curl -u demo-client:secret -X POST http://localhost:9000/oauth2/revoke \
  --data-urlencode "token=<access_token>" --data-urlencode "token_type_hint=access_token"
# => HTTP/1.1 200

# 그런데 revoke 직후에도 resource-server는 여전히 이 토큰을 승인함
curl http://localhost:18081/api/hello -H "Authorization: Bearer <access_token>"
# => HTTP/1.1 200  {"message":"hello, user"}   ← 무효화되지 않음!

원인: resource-server는 spring.security.oauth2.resourceserver.jwt.issuer-uri로 설정된 JWK로 서명만 로컬에서 검증하며(stateless), 매 요청마다 auth-server에 "이 토큰이 아직 유효한가"를 물어보지 않는다. Revocation은 auth-server의 OAuth2AuthorizationService 저장소만 갱신할 뿐이다. 즉시 무효화가 필요하면 resource-server가 로컬 JWT 검증 대신 토큰 introspection(/oauth2/introspect, 매 요청마다 auth-server에 조회)을 쓰거나 opaque token을 써야 한다 — 이 구현은 범위 초과라 하지 않았다(Step 6에서 세션 방식의 즉시 종료와 대비해 같은 결론을 다시 확인함).

대조: 반면 refresh_token은 revoke하면 실제로 막힌다 — refresh 요청은 매번 auth-server의 저장소를 조회하기 때문(stateful):

curl -u demo-client:secret -X POST http://localhost:9000/oauth2/revoke \
  --data-urlencode "token=<refresh_token>" --data-urlencode "token_type_hint=refresh_token"
curl -u demo-client:secret -X POST http://localhost:9000/oauth2/token \
  --data-urlencode "grant_type=refresh_token" --data-urlencode "refresh_token=<same refresh_token>"
# => {"error":"invalid_grant"}  ← 정상적으로 차단됨

실측: 자연 만료 + 60초 clock-skew

테스트를 위해 demo-client의 access-token TTL을 20초로 단축(application.yml의 token.access-token-time-to-live: PT20S)한 뒤 시간을 기록하며 폴링했다.

시각경과결과
20:48:500s토큰 발급 (exp = 발급+20s ≈ 20:49:10)
20:50:07+77s여전히 200 (exp 이후 57초 지났지만 아직 통과 — clock-skew 유예)
20:50:11+81s401로 전환 — 이 시점부터 거부

즉 exp를 정확히 신뢰할 수 없고, 실제로는 exp + 약 60초까지 유효할 수 있다는 뜻이다(Spring Security JwtTimestampValidator 기본값). 엄격한 즉시 만료가 필요하면 JwtTimestampValidator(Duration.ZERO)로 skew를 0으로 좁혀야 한다.

실측: 세션 로그아웃

curl -c c.txt -b c.txt http://localhost:18081/login -o l.html   # 로그인 폼 + CSRF
# ... 로그인 POST ...
curl http://localhost:18081/web/hello -b c.txt                  # 200
curl -c c.txt -b c.txt -X POST http://localhost:18081/logout --data-urlencode "_csrf=..."
# => 302 Location: /login?logout
curl http://localhost:18081/web/hello -b c.txt                  # 다시 302 -> /login (세션 무효화 확인)

참고: resource-server의 /web/** 보안 체인 securityMatcher에 /logout을 추가해야 했다(Step 1에서 /web/**, /login만 포함하고 있었음) — 그렇지 않으면 /logout이 어떤 필터체인에도 매칭되지 않아 404가 발생.

참고 문서

Step 5 — 항목 5: refreshToken 동작 방식

✔ 확인 완료 — grant_type=refresh_token으로 새 access_token을 계속 발급받을 수 있으며, 기본 설정에서는 refresh_token 자체가 매번 새로 교체(rotate)되지 않고 재사용된다는 것을 실측으로 확인했다.

결론 요약

  • access_token을 새로 받아도 refresh_token 값은 그대로 유지된다(TokenSettings.reuseRefreshTokens 기본값이 true이기 때문). 같은 refresh_token으로 여러 번 반복해서 갱신을 요청해도 계속 성공한다.
  • 매 갱신마다 access_token만 새로 발급되고 만료시간도 새로 연장된다(발급 시점 기준 TTL 재적용).
  • 이 기본 동작은 보안상 트레이드오프가 있다 — refresh_token이 한 번 유출되면 그 값 자체가 무효화(rotate)되지 않으므로 탈취된 refresh_token으로 계속 access_token을 새로 받아낼 수 있다. 필요하면 클라이언트 설정에서 reuse-refresh-tokens: false로 바꿔 "사용할 때마다 새 refresh_token으로 교체 + 이전 것은 무효화"하는 rotation 방식으로 전환할 수 있다(이번 데모는 기본값 그대로 두고 동작 차이만 확인, 별도 구현은 하지 않음 — 범위 외).
  • refresh_token의 기본 TTL은 공식 문서 기준 60분이다(이번 데모에서는 access_token TTL만 20초로 단축해 테스트했고, refresh_token TTL 자체의 만료는 60분을 기다려야 해서 실측하지 않음 — 문서값 인용).

실측

# 1) refresh_token으로 access_token 갱신
curl -u demo-client:secret -X POST http://localhost:9000/oauth2/token \
  --data-urlencode "grant_type=refresh_token" --data-urlencode "refresh_token=<refresh_token>"
# => 새 access_token 발급됨. 응답의 refresh_token 값은 요청에 쓴 것과 동일(rotate 안 됨)

# 2) 같은 refresh_token으로 다시 한번 갱신 -> 여전히 성공(재사용 가능)
curl -u demo-client:secret -X POST http://localhost:9000/oauth2/token \
  --data-urlencode "grant_type=refresh_token" --data-urlencode "refresh_token=<동일한 refresh_token>"
# => HTTP/1.1 200 (거부되지 않음)

# 3) 새로 발급된 access_token으로 리소스 접근 확인
curl http://localhost:18081/api/hello -H "Authorization: Bearer <new access_token>"
# => 200

Step 6 — 항목 6: 악의적 사용자 세션 강제 종료

✔ 확인 완료 — 결론: 세션-쿠키 방식은 서버가 즉시 강제 종료할 수 있지만, JWT(토큰) 방식은 만료 전까지 서버가 개입할 방법이 없다. 이번 Step에서 auth-server의 인가 상태를 MySQL(oauth2_authorization 테이블, 공식 JdbcOAuth2AuthorizationService)로, resource-server의 세션을 Redis(spring-boot-starter-session-data-redis)로 옮겨 관리자가 DB/캐시를 직접 조작해 사용자를 쫓아낼 수 있는지 실측했다.

결론 요약

세션-쿠키 (Redis)토큰(JWT)
강제 종료 방법Redis에서 세션 키 삭제 (redis-cli DEL spring:session:sessions:<id>)DB에서 oauth2_authorization 행 삭제 — 하지만 이미 발급된 access_token(JWT)에는 영향 없음
효과즉시 반영 — 다음 요청부터 바로 로그인 페이지로 리다이렉트됨즉시 반영 안 됨 — 만료 시각(exp)까지 계속 유효
refresh_token에는?해당 없음즉시 반영됨 — 삭제 직후 refresh 시도는 invalid_grant

즉, "지금 당장 이 사용자의 접근을 완전히 차단"하고 싶다면 세션-쿠키 방식이 훨씬 유리하다. 토큰(JWT) 방식에서 즉시 차단이 꼭 필요하면 access_token의 TTL을 아주 짧게 유지하고(이번 데모처럼 초 단위), 장기 세션은 refresh_token 쪽으로 넘기는 절충이 일반적이다 — 완전한 즉시 차단이 필요하면 JWT 대신 opaque token + introspection(매 요청마다 auth-server에 조회) 아키텍처로 가야 하는데, 이는 이번 조사 범위를 넘어서 구현하지 않았다.

실측: 세션 강제 종료 (Redis)

# 로그인 후 세션이 Redis에 저장됐는지 확인
docker exec sas-poc-redis redis-cli KEYS "spring:session:sessions:*"
# => spring:session:sessions:642d3d1b-e922-4277-9b04-c5031c4b238a

curl http://localhost:18081/web/hello -b cookies.txt   # 200

# 관리자가 사용자 동의 없이 Redis에서 직접 세션 삭제
docker exec sas-poc-redis redis-cli DEL "spring:session:sessions:642d3d1b-e922-4277-9b04-c5031c4b238a"

# 같은 브라우저 쿠키로 재요청 -> 즉시 로그인 페이지로
curl -i http://localhost:18081/web/hello -b cookies.txt
# => HTTP/1.1 302  Location: http://localhost:18081/login

실측: 토큰은 DB를 지워도 즉시 무효화되지 않음

curl http://localhost:18081/api/hello -H "Authorization: Bearer <access_token>"   # 200

# 관리자가 MySQL에서 직접 인가 레코드 삭제 (Step 2에서 SAS 공식 스키마로 전환한 테이블)
docker exec sas-poc-mysql mysql -uroot -proot sas_poc \
  -e "DELETE FROM oauth2_authorization WHERE principal_name='user';"

curl http://localhost:18081/api/hello -H "Authorization: Bearer <동일한 access_token>"
# => 여전히 200  ← JWT는 자체 서명 검증이라 DB와 무관하게 계속 통과됨

curl -u demo-client:secret -X POST http://localhost:9000/oauth2/token \
  --data-urlencode "grant_type=refresh_token" --data-urlencode "refresh_token=<동일한 refresh_token>"
# => {"error":"invalid_grant"}  ← 이건 즉시 차단됨(AS가 매번 DB 조회)

이번 Step에서 auth-server의 OAuth2AuthorizationService를 인메모리에서 JdbcOAuth2AuthorizationService(MySQL)로 교체했다. RegisteredClientRepository는 그대로 property 기반(인메모리)으로 유지 — 이번 조사 질문(강제 종료 가능 여부)에는 인가/토큰 저장소만 바뀌면 충분하기 때문에 범위를 넘기지 않았다.

추가 확인: /oauth2/revoke + /connect/logout 조합으로는 즉시 차단이 되는가?

✔ 확인 완료 — 여전히 불가능하다. access_token과 refresh_token을 둘 다 revoke하고, 거기에 OIDC RP-Initiated Logout(/connect/logout)까지 호출해도 원래 발급된 access_token은 여전히 resource-server를 통과한다.

curl -u demo-client:secret -X POST http://localhost:9000/oauth2/revoke \
  --data-urlencode "token=<access_token>" --data-urlencode "token_type_hint=access_token"     # 200
curl -u demo-client:secret -X POST http://localhost:9000/oauth2/revoke \
  --data-urlencode "token=<refresh_token>" --data-urlencode "token_type_hint=refresh_token"    # 200
curl "http://localhost:9000/connect/logout?id_token_hint=<id_token>" -b cookies.txt          # 302 (로그아웃 성공)

curl http://localhost:18081/api/hello -H "Authorization: Bearer <동일한 access_token>"
# => 여전히 200 ← 셋 다 실행해도 이미 발급된 JWT는 막지 못한다

이유: 세 엔드포인트 각각이 하는 일이 서로 다른 상태를 건드리기 때문이다.

  • /oauth2/revoke — auth-server의 oauth2_authorization 레코드를 지운다(=앞으로의 refresh나 introspection 조회에는 영향).
  • /connect/logout — auth-server 자신의 브라우저 로그인 세션(SecurityContext)을 끝낸다. 실제로 로그아웃 후 같은 쿠키로 /oauth2/authorize를 다시 호출하면 재로그인이 요구되는 것으로 확인했다(외부 React 로그인 페이지로 재리다이렉트됨). 하지만 이건 "다음 로그인부터"에 영향을 줄 뿐, 이미 브라우저/클라이언트에 나가 있는 access_token과는 전혀 무관하다.
  • resource-server는 이 두 상태 중 어느 쪽도 조회하지 않는다 — 오직 JWT 서명이 유효하고 exp가 안 지났는지만 로컬에서 확인한다. auth-server 쪽에서 무엇을 revoke하거나 logout하든, resource-server의 로컬 검증 로직 자체는 전혀 바뀌지 않는다.

즉 세 엔드포인트를 다 동원해도 "토큰을 들고 있는 쪽(resource-server)이 매번 물어보게 만들지 않는 한" 즉시 차단은 구조적으로 불가능하다. 실제로 즉시 차단이 필요하면 resource-server의 spring.security.oauth2.resourceserver.jwt.* 설정을 opaque-token.introspection-uri 기반으로 바꿔 매 요청마다 /oauth2/introspect를 호출하도록 해야 한다(그러면 revoke 직후 introspection 응답이 active: false로 바뀌어 즉시 막힌다). 이번 조사는 "가능한지" 판단이 목적이라 이 전환은 구현하지 않고 결론만 남긴다.
